# Участие в разработке Wumpo

Wumpo — эксперимент по созданию консоли размером с брелок. Ограничение —
64×32 пикселя, шесть кнопок, никакой плавающей точки — это суть проекта, а не
препятствие, которое надо обойти.

## Прежде чем начать (Definition of Ready)

- Ты можешь одним предложением сказать, что должно получиться.
- Понятно, каких файлов и модулей это касается.
- Понятно, как проверить результат: тест, golden-эталон или описанная ручная
  проверка.
- Если изменение архитектурное — есть черновик ADR в `docs/decisions/`.

## Прежде чем закончить (Definition of Done)

Того, что код компилируется, недостаточно. Изменение готово, когда есть код,
тесты, обновлённая документация там, где изменилось поведение или установка,
применён `clang-format`, чист `clang-tidy`, зелёный CI и проведена ручная
проверка. Визуальные изменения требуют скриншота или описанного наблюдения.

Для геймплейной работы дополнительно: играбельно, работает рестарт, работает
game over, детерминировано, replay воспроизводит результат, нет очевидных багов
ввода.

## Рабочий процесс

`main` всегда в рабочем состоянии. Крупная работа идёт в ветках `feature/...`,
`fix/...`, `refactor/...` или `prototype/...`.

```powershell
.\scripts\dev.ps1 build
.\scripts\dev.ps1 test
.\scripts\dev.ps1 format
.\scripts\dev.ps1 lint
```

Коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(renderer): add monochrome framebuffer
fix(input): prevent repeated key events
test(core): add deterministic tick tests
```

Типы: `feat fix refactor test docs build ci perf chore style revert`.
Один коммит — одно логическое изменение. Никогда не смешивай фичу с несвязанным
рефакторингом, документацией и обновлением зависимости. Сообщения вида `update`,
`fix`, `stuff` или `final2` недопустимы. Не добавляй трейлеры соавторства.

Тексты коммитов пишутся на английском — это часть соглашения Conventional
Commits и то, что видят внешние инструменты. Документация — на русском.

## Правила кода

C++20. Правила детерминизма из [CLAUDE.md](CLAUDE.md) обязательны: никакой
плавающей точки, системных часов и `<random>` в симуляции, никаких аллокаций во
время игры. `src/core` и `src/game` никогда не включают заголовок бэкенда.

Код и комментарии в коде пишутся на английском, документация — на русском.

Предпочитай наименьшую корректную реализацию наибольшей возможной абстракции.
Интерфейс с одной реализацией и без второй на горизонте — не абстракция, а
накладные расходы. Исключение — граница платформы, где вторая реализация и есть
весь смысл.

## Добавление зависимости

Ответь на все вопросы в pull request и запиши результат в `THIRD_PARTY.md`:

1. Что она делает такого, чего не может стандартная библиотека?
2. Поддерживается ли она?
3. Какая у неё лицензия и совместима ли она с MIT?
4. Какова цена — размер бинарника, время сборки, сложность компиляции?
5. Не помешает ли она будущей embedded-сборке (аллоцирует ли, бросает ли
   исключения, нужна ли ей ОС, RTTI, исключения)?

Никогда не копируй код неизвестного происхождения. Сторонние ассеты требуют
задокументированного происхождения и разрешения.
